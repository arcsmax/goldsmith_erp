# ADR 2026-09-25: One media table, one store, one service

Status: accepted. Architecture review phase "4. Media"
(docs/review/2026-09-25/01-architecture.md, section E).

## Context

Photos lived in three tables with three near-identical services:
`order_photos` (uuid ids), `repair_photos` (integer ids, a phase) and
`consultation_photos` (uuid ids, a kind). Each service wrote files to its
own directory under `PHOTO_STORAGE_PATH`, derived thumbnails by path
convention and unlinked files itself. Nothing recorded a file's size, hash
or dimensions, and there was no way to say "this photo may be shown to the
customer", so the Kundeninfo e-mail and the status report guessed from
which photos had already been ticked into sent messages.

## Decision

1. **`media_assets` table** (`db/models/media.py`): one row per stored
   file, `owner_type` (order / repair / consultation / customer_update) +
   `owner_id` as a polymorphic reference, `kind` (photo / signature /
   document), `storage_key`, `mime`, `bytes`, `width`, `height`, `sha256`,
   `customer_visible` (default false), `caption`, `sort_order`, `taken_at`,
   `uploaded_by`, `created_at`, `deleted_at` (soft delete). Enumerations
   are strings with CHECK constraints (no `ALTER TYPE` for new values).
   Two bridge columns, `legacy_id` and `tag`, link a row to its deprecated
   source row and carry that row's phase or kind.
2. **`MediaStore`** (`services/media_store.py`): `put(bytes, mime) -> key`,
   `open(key)`, `delete(key)`, `url_for(key)`. `LocalMediaStore` keeps the
   same root as before (`PHOTO_STORAGE_PATH`). New keys are content
   addressed: `{owner-dir}/{sha256[:2]}/{sha256}.{ext}`, thumbnail in the
   `thumbs/` sibling. The owner directory is the old one (`42`,
   `repairs/7`, `consultations/3`), so equal bytes are stored once per
   owner, and an Art. 17 erasure of one customer can never unlink a file
   another customer's row still points at. Old absolute paths are valid
   keys too (compatibility branch), always anchored to the root.
3. **`MediaService`** (`services/media_service.py`): the one upload
   pipeline (size/type/bomb checks, EXIF stripped and orientation applied
   off the event loop with a timeout, content-addressed write, bounded
   200 px thumbnail), asset lookup, refcounted delete (a shared file is
   unlinked with its last live row) and owner-based authorization: every
   read needs `DESIGN_VIEW` (design IP, VIEWER gets 403) plus the owner's
   view permission; edits need the owner's edit permission.
4. **Deprecation, one release.** The three photo services delegate to
   `MediaService` and keep writing their legacy row (dual write), so every
   existing endpoint, PDF, e-mail, erasure path and test keeps working. The
   migration `20260925_arch4_media` copies all existing rows (sizes and
   sha256 recomputed for files that exist; missing files logged, not fatal;
   rows already erased skipped). Order and consultation assets reuse the
   legacy uuid as their id; repair assets get a new uuid.
5. **New endpoints**: `GET /media?owner_type&owner_id`, `GET /media/{id}`,
   `GET /media/{id}/thumbnail`, and `PATCH /media/{id}` for the
   `customer_visible` flag (GOLDSMITH/ADMIN). Registered with the audit
   middleware (`media` family, every verb). `storage_key` is never
   returned.
6. **GDPR / backup**: the file-erasure sweep redacts the customer's
   `media_assets` rows (key -> `[REDACTED_PATH]`, caption and hash cleared,
   soft-deleted) and unlinks any file only they reference. `scripts/backup.sh`
   archives the media root next to the database dump, encrypted the same way.

## customer_visible semantics

* Status report: the owner's `customer_visible` photos (newest first, up to
  six) when any are flagged, else today's rule (photos already sent to the
  customer for orders, the latest photos for repairs). The PHOTO_USE consent
  check is unchanged.
* Kundeninfo: explicitly ticked photo ids always win, as today. A photo
  message (`photo_update`) sent with no ticked photos uses the flagged
  photos. Text-only messages never pick up photos implicitly, so no message
  starts to need photo consent because a flag was set.

## Consequences

* Next release: switch readers (PDF, e-mail, scanner, order list thumbnail)
  to `media_assets`, then drop the three legacy tables and the dual write.
* An object store (S3/MinIO) is a second `MediaStore` implementation;
  `url_for` would return a presigned URL. Not needed for a single box.
* Deleting an order/repair/consultation row does not yet soft-delete its
  assets (no FK); the erasure sweep covers the GDPR case, a periodic orphan
  sweep is an open item.
